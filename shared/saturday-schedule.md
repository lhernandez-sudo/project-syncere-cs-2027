# Four-Hour Saturday Schedule

Use this structure as the default plan for a 9:00 AM-1:00 PM class. It provides 220 instructional minutes and 20 minutes of breaks.

| Time | Minutes | Block | Purpose |
| --- | ---: | --- | --- |
| 9:00-9:20 | 20 | Do-now or CS challenge | Activate prior knowledge with a short, approachable problem. |
| 9:20-9:40 | 20 | Community, review, and objectives | Connect, review the previous lesson, and preview the day's outcome. |
| 9:40-10:25 | 45 | Lesson and live coding | Introduce one focused concept with questions and predictions. |
| 10:25-10:35 | 10 | Break | Step away from screens. |
| 10:35-11:20 | 45 | Guided Python lab | Practice the new concept with instructor support. |
| 11:20-11:30 | 10 | Break | Reset before sustained project work. |
| 11:30-12:25 | 55 | Project or challenge | Apply the concept to a meaningful artifact. |
| 12:25-12:45 | 20 | Share, debug, and peer review | Explain decisions, test programs, and exchange feedback. |
| 12:45-1:00 | 15 | Exit ticket and reflection | Record learning, remaining questions, and the next step. |

## Planning principles

- Limit direct instruction to one main concept at a time.
- Type and run code frequently during demonstrations.
- Plan a working artifact for every class, even if it is small.
- Include extension tasks without making them required for beginners.
- Normalize errors by discussing at least one debugging example each week.
- Use the reflection to adjust the following Saturday's opening review.

## Project-day variation

On build days, keep the opening check-in, both breaks, peer review, and reflection. Combine the lesson and guided-lab blocks into a longer planning or development session when students need sustained work time.
